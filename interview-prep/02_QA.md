# 面试 Q&A 准备

## 关于项目整体

**Q: 这个项目解决什么问题？**
A: LeetCode 学习效率低的问题。学生刷题时没有结构化的学习路径，不知道从哪里开始；遇到问题时只能看静态题解，没有针对自己代码的个性化反馈。AlgoMentor 提供：知识点路线图 → 文章学习 → 代码练习 → AI 实时辅导的完整闭环。

**Q: 用了哪些技术？为什么这样选？**
A: Backend 用 FastAPI 因为原生支持 async，适合同时处理多个 AI API 调用和数据库查询。PostgreSQL 加 pgvector 扩展做向量搜索，这样 RAG 和关系数据在同一个数据库，不用维护额外的向量数据库。代码执行用 Piston（Docker-based sandbox），保证隔离性同时支持 12 种语言。

## 关于安全执行环境

**Q: Docker sandboxing 具体怎么实现的？**
A: 使用 Piston 作为执行引擎，它本身是开源的 Docker-based 代码执行平台（github.com/engineer-man/piston）。每次代码提交创建一个全新的 Docker 容器，执行完立即销毁。容器配置了：
- 网络隔离（no network access）
- 文件系统隔离（只有临时目录）
- 内存限制：128MB
- CPU 时间限制：5 秒
- 编译超时：10 秒

在生产环境会部署 self-hosted Piston 实例，不依赖公共 API。

**Q: 如果用户提交 `while True: pass` 死循环怎么办？**
A: Piston 的 `run_timeout` 参数设置了 5000ms 超时，超时后容器会被强制终止，返回 timeout 错误给用户。不会影响其他用户的执行。

**Q: 如果用户提交 `import os; os.system('rm -rf /')`？**
A: Docker 容器的文件系统是隔离的，`rm -rf /` 只会删除容器内的临时文件，不影响宿主机。容器执行完后销毁，下次执行是全新的环境。网络隔离确保代码不能访问外部资源或宿主机网络。

**Q: Cgroup 资源限制是怎么配置的？**
A: Piston 底层通过 Docker 的 `--memory` 和 `--cpus` 参数来设置 Cgroup 限制。在我们的 API 请求里，`run_memory_limit` 设为 128MB，Piston 会把这个参数转换为对应的 Cgroup 配置。Cgroup v2 通过 `/sys/fs/cgroup/memory.max` 控制内存上限，超出后进程收到 OOM kill 信号。

## 关于 RAG 功能

**Q: RAG 是什么？你是怎么实现的？**
A: RAG（Retrieval-Augmented Generation）是在调用 LLM 之前，先从知识库检索相关内容作为上下文，让 AI 的回答基于具体资料而不是通用训练数据。

我的实现：
1. 把 KnowledgePoint 的文章内容按段落切块（chunk_size=500 字符，overlap=50）
2. 用 `sentence-transformers` 的 `all-MiniLM-L6-v2` 模型生成 384 维 embedding
3. 存入 PostgreSQL 的 `knowledge_embeddings` 表（pgvector 扩展）
4. 用户提问时，把问题转成 embedding，用余弦相似度搜索 top-3 最相关片段
5. 把检索到的片段作为 context 注入 system prompt，再调用 SiliconFlow LLM

**Q: 为什么用 pgvector 而不是 Pinecone / Weaviate？**
A: 对于这个项目的规模（知识点数量有限），pgvector 完全够用。主要优势：
- 不需要额外维护一个独立的向量数据库服务
- 可以在同一个查询里结合向量相似度和关系过滤（比如只搜索特定 knowledge_point 的 chunks）
- 事务一致性：文章更新和 embedding 更新可以在同一个事务完成
- 成本低：复用已有的 PostgreSQL

**Q: embedding 模型为什么选 all-MiniLM-L6-v2？**
A: 这是 sentence-transformers 里性价比最高的模型之一：
- 384 维，存储空间小
- 本地推理，无 API 费用，无网络延迟
- 在语义相似度任务上表现很好
- 推理速度快，1000 个 chunk 几秒内完成

如果需要更高精度，可以换 `text-embedding-3-small`（OpenAI）。

**Q: RAG 有什么局限性？你怎么处理？**
A: 主要局限：
1. 如果知识库里没有相关内容，检索到的 chunks 可能噪音很大 → 用相似度 threshold 过滤，低于 0.5 的不使用
2. Chunk 的边界可能切断上下文 → 用 sliding window overlap 保证连贯性
3. Embedding 模型对代码的理解不如对自然语言 → 代码相关问题可以 fallback 到直接的 LLM 问答

## 关于 Rate Limiting

**Q: Rate limiting 是怎么实现的？**
A: 用 SlowAPI 库（FastAPI 的 rate limiting 中间件），后端用 Redis 存储计数器。
- 代码执行接口：每 IP 每分钟 10 次
- AI 聊天接口：每 IP 每分钟 20 次
- Key 是客户端 IP（`X-Forwarded-For` header 或直接连接 IP）
- 超限返回 429 Too Many Requests，`Retry-After` header 告诉客户端等待时间

**Q: 没有 Redis 的时候怎么办？**
A: SlowAPI 支持内存存储作为 fallback。单实例部署时内存存储够用，多实例部署时需要 Redis 保证跨实例的计数一致性。

## 关于数据库设计

**Q: 你的 ORM 是怎么用的？**
A: SQLAlchemy 2.0 的 async 模式，用 `AsyncSession` + `asyncpg` 驱动。所有数据库操作都是 `await`，不阻塞事件循环。使用 `select()` 的 ORM 风格而不是 raw SQL，自动防 SQL 注入。

**Q: 数据库迁移怎么管理？**
A: Alembic，每次 schema 变更生成 migration 脚本，`alembic upgrade head` 应用迁移。可以回滚。

## 关于 JWT 认证

**Q: JWT token 里存了什么？过期策略？**
A: Token payload 里只存 `user_id`（`sub` claim）和 `exp`（过期时间）。不存用户名/邮箱等敏感信息。Token 有效期 7 天，前端存在 localStorage，退出登录时删除本地 token（服务端无状态，不做 blacklist）。

**Q: 如果 token 泄露怎么办？**
A: 当前实现是无状态 JWT，token 泄露后在过期前无法撤销（这是 JWT 的典型权衡）。生产场景可以加 token blacklist（存 Redis），或改用短 token（1小时）+ refresh token 机制。

## 关于项目的不足（主动提及，展示诚实和思考深度）

**你会怎么改进这个项目？**
A: 几个方向：
1. **代码执行**：部署 self-hosted Piston 而不是用公共 API，可以更细粒度控制资源，加 queue 处理高并发
2. **RAG 质量**：加 reranker（cross-encoder）做二次排序，提升检索精度；加用户反馈收集，持续优化
3. **个性化**：记录用户做题历史，用强化学习推荐下一道题（类似 Anki 的间隔重复）
4. **监控**：加 Prometheus + Grafana 监控代码执行成功率、AI 响应时间
